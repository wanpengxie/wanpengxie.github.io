> 状态：架构定位（系列第一篇）  
> 当前判断：Atoll 已实现持久协作 substrate；完整 Agent OS 系统层尚未实现。  
> 本篇回答一个问题：把 agent loop 做到极致，为什么仍然得不到一个 Agent OS——差的不是工程量，是问题本身换了。

## 1. Loop 这一层已经被做得很好

成熟 coding agent 的核心是一条反馈循环：

```text
user input
   ↓
model sampling
   ↓
tool calls
   ↓
tool results
   └──────────▶ next sampling
```

Codex 和 OpenCode 已经证明，这条循环需要一整套精细语义：input queue、steer、
interrupt、approval、compaction、tool 并发、subagent。Lilian Weng 在
[Harness Engineering](https://lilianweng.github.io/posts/2026-07-04-harness/)
里把这一层总结为 harness——围绕基础模型、决定它如何思考规划、如何调工具行动的系统——并给出了
harness 的关键模式：文件系统作持久记忆、子 agent 显式并行、输出落盘可检查。她写道，
harness 应该像 OS 一样封装复杂逻辑、保持接口简单。

这一层的问题是真实的、难的，而且远没有做完。但要看清它回答的是哪一个问题：

> 一个 agent session 怎样有效地继续执行？

harness 的 OS 类比也是在这个范围内成立的：它封装的是**一个模型的执行周边**。
文件系统、子 agent、日志、记忆，最终都服务于同一个 session、同一个主体的继续推进。
这是执行器（executor）的世界。

## 2. 换一个问题：第二个主体进来之后

OS 级的问题不是"下一次调用哪个模型"，而是从**多个互相独立的主体——人、属于不同人的
agent、服务、设备——进入同一个持久世界**的那一刻开始的：

- 谁拥有长期身份和权限？一个 agent 断线重连之后，还是不是原来那个执行者？
- 多个参与者共享的事实写在哪里？谁有权写？
- 进程崩溃后，协作关系如何恢复？旧实例还能不能继续写？
- Agent 和数据跨机器移动时，怎样保持同一套语义？
- 两个自治空间怎样交接工作，而不共享可变真相？
- 一个构建出来的 App 如何安装、升级、回滚、持续运行？

这些问题不是"更大的 loop"。loop 工程做得再深也不会自动回答它们，因为它们关心的
不是一次执行的内部，而是**执行与执行之间、主体与主体之间的世界**。session 可以结束、
崩溃、被替换，世界必须还在，而且必须仍然可解释。

所以这个系列的第一个判断是：session loop 是优秀 Agent Runtime 的执行器，
不是 Agent OS 的架构。二者不是程度差异，是问题域差异。

## 3. OS 意味着一个封闭的语义宇宙

"OS"这个词经常被当作比喻用。我们不打算比喻，先把它的实义说清。

一个系统成为 OS，不在于它功能多，而在于它对自己声明管辖的领域建立了一个
**封闭的语义宇宙**：所有第一类对象、所有有效状态变化，最终都只能由它的抽象来描述，
由它的运行时来裁决。不存在另一套并列的、未经它解释的系统语义。

Linux 是最好的例子——而且它说明封闭性与"原创抽象"无关。process、fd、file、socket
这些概念是 Unix 发明的，Linux 没有原创它们；Linux 做成的事情是**实现并封闭了这台
抽象机器**。数据库事务、Git commit、HTTP 请求都不是 Linux 对象，它们最终都被归约成
进程执行、内存读写、文件读写、socket 通信、系统调用、权限检查。应用可以定义任何概念，
但这些概念不会成为内核里的平行宇宙。

封闭有三层，一层比一层硬：

1. **对象封闭**——系统直接认识的第一类对象来自一个明确集合；
2. **状态迁移封闭**——这些对象的创建、改变、转移、失效，只能通过系统规定的操作发生；
3. **裁决封闭**——不仅"理论上可以这样表达"，而且实际行为**绕不开** runtime。

第三层是 library 和 OS 的根本分界。Library 说：请按照我的类型和约定组织代码。
OS 说：你对我所管理世界的任何有效影响，都必须经过我。只拥有一套漂亮的数据结构
不构成系统；系统必须有执行上的 full mediation。

Atoll 的目标就是对 agent 协作世界建立这三层封闭。它的五元素本体
`{channel; actor, resource; message, access}` 由
[第二篇](/2026/08/04/five-elements-two-planes/)展开；这里只需要先立住标准：判断 Atoll 是不是 OS，不看它定义了什么，
看它管辖的世界里**还存不存在第二种存在方式**。

## 4. 封闭的是规律，不是实体数量

这里要立刻排除一种误读：封闭的语义宇宙 ≠ 极简的对象名录。

Linux 并不是五个漂亮概念的纯净代数。它内部有 task_struct、mm_struct、inode、dentry、
namespace、cgroup、epoll、io_uring——大量真实而复杂的工程对象，各有自己的状态机、
生命周期和恢复流程。"everything is a file" 只是设计口号的近似。这些对象没有破坏
封闭性，因为它们全部生活在同一套系统法律之下：同一套身份与 credential、同一套调度、
同一套权限检查、同一条 syscall 入口。

所以应该极简的是**系统规律的种类**，不是 struct 和状态机的数量：

> 封闭的是物理规律，开放的是工程实体。

一个协作系统可以有 Job、Review、Approval、Lease、Workspace——一百个工程对象都没问题。
真正的危险信号是出现一百套**规律**：Job 服务自己维护一份用户身份、一套 ACL、一套
heartbeat、一套重试队列、一份审计日志；Share 服务再来一遍；Workspace 服务又来一遍。
每个服务各自长出一个小内核。这时无论单个服务写得多好，它们一组合，
边界问题就在缝隙里重新长出来。

系统最应该压缩的不是实体数量，而是法律数量：

> 可以有一百个对象，但不应该有一百套"谁是谁、谁能做什么、谁还活着、发生了什么"的答案。

Atoll 对自己的要求因此不是"世界里只能存在五种东西"，而是：**只有一套身份、边界、
因果、权限、生命周期和时间语义；所有运行时实体与上层服务都生活在这套语义之下。**
新增一个工程对象随时可以；新增第二套身份模型、第二份真相、第二个时间来源，不行。

## 5. 封闭为什么值得：坏复杂度变成不变量

封闭不是审美偏好，它是系统处理复杂性的手段。

协作系统里真正难缠的复杂度，不是业务本身，而是多个机制交叉出来的边界情况：

```text
并发 × 失败 × 重试 × 权限 × 生命周期 × 时间
```

一次工具调用的常规路径很简单：Agent → Tool → Result。系统问题藏在旁边：
执行成功但回复丢了怎么办？agent 断线重连后还是不是原执行者？新实例已经接管，
旧实例又提交结果怎么办？权限在调用中途被撤销怎么办？重试会不会产生重复副作用？
daemon 崩溃之后 timer 还在不在？成员退出之后，它手里的旧能力什么时候失效？

如果每个应用、每个服务、每个 agent 都自己处理这些问题，复杂度按乘积增长——
而且每一份处理代码本身又是新的出错面。系统的作用是把它们压进少数几条全局不变量，
让整类坏状态**在结构上不可能成为有效状态**，而不是被更小心地处理。举 Atoll
已经建成的几条：

- **发送者不可伪造**：写入身份在能力（pen）出生时焊死，不信任何自报字段；
  一个 actor 化身死亡后，它泄漏给后台任务的写能力在写入点被拦截——"死人写活账"
  这一类冒充，不需要任何上层代码防范，因为写不进去。
- **单写路径**：channel 真相只有一条结构上的写入口，七步校验，任一步拒绝则事实
  不产生。不存在"绕过写门直接落库"的代码路径，所以也不存在这类 bug。
- **精确身份**：清理与回调只认物理实例的 exact 身份，不按逻辑名字猜继任者——
  经典 ABA（迟到的消息打在同名新实例上）失去存在语法。
- **重启第一拍等于平时一拍**：不存在专门的崩溃恢复路径。重启后系统读到的就是
  日常收敛逻辑的普通输入。"恢复代码自己有 bug"这一整类问题随恢复路径的不存在而消失。
- **因果必收敛**：带 deadline 的请求是写入时焊进真相的持久义务，"每个未决请求
  终将闭账"由存储层唯一性约束硬保证，不靠调用方自觉。

注意这些例子的共同形状：不是"帮上层把异常处理写好了"，而是让错误组合**造不出来**。
这正是内核与框架的分工差异——

> 内核负责让错误组合不成立，平台负责让正确组合足够便宜。

这也是为什么 agent 世界比传统 OS **更**需要封闭而不是更不需要。agent userspace
比 Linux 的 userspace 更敌意：驱动它的是非确定的、可被注入的 LLM，组装它的是
不受我们控制的人。约定式的约束——文档、code review、prompt 里写"请不要"——在
agent 消费模型下约等于零强制。由构造守住的契约在这里承重更重，不是更轻。
检验一条不变量是否真正封闭，只需要一问：**一个我们不控制的下游组装者，
能不能破坏它？**

## 6. Atoll 的管辖边界：进入共享世界的那一刻

封闭的语义宇宙需要一条明确的边界：封闭到哪里为止。

Atoll 不吞下整个 agent 世界。LLM 如何推理、harness 如何压缩上下文、agent 内部
如何规划、本地代码如何执行、用户未共享的私人文件如何组织——这些属于 agent 的本地
世界和宿主系统，正是第 1 节里 loop/harness 层的领地，Codex、OpenCode 和
Lilian Weng 总结的那些模式在那里继续适用。Atoll 真正管辖的是：

> 多个独立主体进入同一个持久协作世界之后发生的一切。

Linux 不理解进程内的每一次加法，但进程要打开文件、访问网络、影响共享世界，
就必须进入 syscall。同样，Atoll 不理解 agent 的每一步思考，但一个主体要：

- 把结果变成共同事实；
- 访问他人共享的资源；
- 委托另一个主体做事；
- 获得或让渡权限；
- 邀请新成员、交接工作；
- 产生外部副作用；

就必须进入 Atoll 的语义。共享边界就是 Atoll 的系统调用边界。外部世界的
Codex、浏览器、Git repo、远程工具并没有消失，它们在穿过边界时被投影成世界内的
公民：执行 agent 是 Actor，远程工具是 Actor，代码与素材是 Resource，调用工具是
Access，邀请与交接是 Message 协议。对 Atoll 世界而言，它们不再携带第二套系统语义。

这条边界让 Atoll 成为一个可行的 overlay OS：它不替代 Linux，不替代模型 runtime，
也不与任何 harness 竞争——它管的是它们之间那个此前无人管辖的共享世界。

## 7. 今天的 agent 系统：能力很多，宇宙没有

用这个标准看现状会很清楚。今天多数 agent 项目的典型结构是：

```text
LLM API      提供推理          Git        提供版本世界
Host OS      提供进程/文件     数据库      提供状态
MCP          提供工具接口      queue/cron 提供任务和时间
容器          提供隔离          framework  用代码和 prompt 粘起来
```

它们定义 Agent、Session、Tool、Memory、Task、Workflow，但这些多数是应用结构，
不是封闭世界的内核对象：身份常常只是一次进程或 session ID；工具权限来自环境变量
而不是统一的授权模型；任务状态在一张表里，记忆在向量库里，副作用直接经 HTTP 发生；
Git、文件系统、消息系统各自持有不同真相。能力很多，却没有统一的归约边界。

这不是贬低——绝大多数优秀软件本来就是组合软件，它们**使用**现有系统的世界。
区别只在于它们没有建立新的封闭世界，于是一旦工作跨越主体、跨越机器、跨越 session，
边界问题就重新落回每个应用自己手里。我们对十余个开源 agent 系统做过逐家源码拆解，
几个有代表性的观察（均基于当时调研的版本）：

- **有 log 不等于有基座。** OpenHands 是认真做了事件溯源的：物理上 append-only
  的事件树、不可变事件、fork 即移动指针。但控制状态活在另一份就地覆写的快照文件里，
  与事件流并列而不互相派生；事件在跨进程边界时被复制两到三份，前端轮询的是第三份副本。
  log 是必要的，但没有身份、边界和写门把它变成唯一真相，log 就退化成高级记录仪。
- **真相形态在整个品类里单调收敛。** 把各家的会话真相排成一条谱：散文件 →
  可变单表（goose 的 SQLite，compaction 靠删行重插）→ 不可变事件（OpenHands）→
  更年轻的 opencode 已经独立建出 per-aggregate 序号、写门、mailbox。出生越晚的系统，
  离"log 即真相 + 门 + 单写口"越近。这条渐近线不是我们画的，是品类自己在漂移。
- **协作是全场性的负空间。** 头部几家合计几十万 star，覆盖个人工具到企业平台，
  本体里都没有多主体协作的位置；需求真来了就外挂 IM 桥、CRDT、webhook。
  这说明的不是"没人需要协作"，而是单 agent 工具的引力井极深，
  **下游长厚之后，共享世界的结构位置塞不回去**——它必须在 day-1 就留好。
- **约定挡不住并发。** 一个由 AI 编队高吞吐开发、零 peer review 的系统，
  跑在"文件系统即身份即真相"的底座上，产出了稳定的 race 与数据丢失 bug 流——
  而且 bug 精确扎堆在缺少不变量的坐标上。工序纪律能续命，代替不了结构强制。

这些系统在各自的目标上都做得很好。它们共同空出来的，恰好是第 3 节定义的那个东西：
一个封闭的、多主体的、持久的语义宇宙。

## 8. 诚实的现状与本系列的路线

按本系列的状态约定（**已实现 / 架构可支持 / 探索中**）：

- **已实现**：一个扎实的单 Channel 协作 substrate——单点全序的真相日志、
  构造级的单写路径、不可伪造的发送者身份、闭集词汇边界、成员/在线分离、
  cell 崩溃隔离。第 5 节列举的不变量能在当前代码中逐条定位。
- **架构可支持**：Codex-like、OpenCode-like 的 Agent Runtime 作为 Channel 内
  系统层嵌入（第五篇，待发）；durable multi-agent 协作。
- **探索中**：跨 Channel 关系与联邦（第六篇，待发）、安装式 App Runtime
  （第七篇，待发）；沙箱与机密性/凭据切片尚未建成，配额与反压只有局部——
  完整清单见第八篇（待发）。

最后把 Atoll 的命题按本篇的语言重新说一遍。Atoll 的目标不是"用五个抽象描述协作"——
描述能力从来不稀缺。它的目标是：**所有进入共享世界的协作行为，除了这套基元及其组合
之外，再无第二种存在方式。**在此之上还有一个更强的赌注：这个基底可以很小。
小基底若成立，组合与推理的收益巨大；但它是需要被真实 workload 验证的设计主张，
不是 OS 成立的逻辑前提。本系列接下来的文章，就是把这两件事——封闭性怎么建立、
小基底怎么检验——逐层展开。
